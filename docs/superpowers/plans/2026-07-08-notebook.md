# Notebook Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Give students a per-day, optionally per-subject notebook — attached to the School System, synced the same way, with schema-versioned export/import — so their daily reflections accumulate into a visible development journal.

**Architecture:** Notes live in the *same* `useSchoolStore` created in the School System epic (PRD Epic B) — no new store, no new sync writer. One note is uniquely keyed by `(date, subjectId)`; `subjectId: null` means a general daily note. `schoolSync` (already wired in `syncManager.js`/`sessionBootstrap.js`) grows to carry `notes` alongside `subjects`/`scheduleSlots`/`appointments`. Export/import mirrors ADR-0001's Roadmap export pattern exactly: a small versioned pure-function schema module, wired to a Blob-download/hidden-file-input pair in the UI, following `RoadmapPage.jsx`'s existing `downloadSchema`/`handleImportFile` shape.

**Tech Stack:** Zustand + `persist` (existing `useSchoolStore`), Firebase Firestore (existing `users/{uid}.school` field), Vitest + `@testing-library/react` (jsdom), React, Tailwind v4 tokens, lucide-react icons.

## Global Constraints

- **No TypeScript** — plain JS + JSX only. No type annotations.
- **No new store, no new sync writer, no new Firestore field path.** Notes extend the existing `useSchoolStore` and its existing `schoolSync` (`src/lib/syncManager.js`); they persist inside the existing `users/{uid}.school` object, alongside `subjects`/`scheduleSlots`/`appointments`. Do not create `useNotebookStore` or a separate `notes/{uid}` document.
- **No Firestore rules change** — the existing `users/{uid}` owner-write-except-`coins` rule already covers the `school.notes` field, exactly as it already covers `school.subjects`/etc. (see Epic B's plan, `2026-07-08-school-system.md`, Task 7 Step 3).
- **Export/import schema is versioned and store-independent**, mirroring ADR-0001 (`docs/adr/0001-roadmap-export-schema.md`) and its implementation `src/utils/roadmapExport.js`: a pure `toSchema`/`fromSchema`-style pair, `{ version, ... }` envelope, throws on an unsupported/missing version. IDs and timestamps are never part of the exported file — import regenerates them via the same `upsertNote` merge path a normal edit uses, so re-importing a file can never collide with existing note ids.
- **File I/O mirrors `RoadmapPage.jsx`'s existing pattern** (`src/pages/RoadmapPage.jsx:200-232`): a `Blob` + `URL.createObjectURL` + a synthetic `<a download>` click for export; a hidden `<input type="file">` + `file.text()` + `JSON.parse` + try/catch with a `window.alert` fallback for import.
- **Tailwind v4 tokens** — reuse existing classes (`neo-card`, `neo-btn`, `thai-font`, `pixel-font`, `text-danger`) — no new tokens.
- **Naming conventions**: store actions are verbs (`upsertNote`, `removeNote`, `importNotes`); pure helpers live in `src/utils/`; tests colocated as `Name.test.js(x)`.
- **Visual fidelity**: complete, functional, tested screens using the existing design system — not pixel-perfect wireframe reproduction (same stance as Epic B; see `CLAUDE.md`'s collaboration model).

**Background (why):** PRD issue #36, Epic C. The wireframe's "Subject Name | Description/Create" screen shows a **Notebook** section with import/save/export controls beneath Schedule and Appointment; the day view shows a note pill under each subject. This epic is exactly that piece — Epic B (School System, already shipped: commits `36a5fb8`..`196ef22`) deliberately left it out of scope.

**Data model (extends Epic B's `useSchoolStore` state):**

```js
// notes: [{ id, date, subjectId, text, createdAt, updatedAt }]
//   date: 'YYYY-MM-DD' string
//   subjectId: a subject id string, or null for a general (not subject-tied) daily note
//   at most one note exists per (date, subjectId) pair — upsertNote enforces this
```

```js
export function noteFor(notes, date, subjectId = null) {
  return notes.find((n) => n.date === date && (n.subjectId ?? null) === subjectId)
}

export function notesForSubject(notes, subjectId) {
  return notes
    .filter((n) => n.subjectId === subjectId)
    .sort((a, b) => a.date.localeCompare(b.date))
}
```

```js
// Notebook export schema — mirrors ADR-0001's Roadmap export approach
// (docs/adr/0001-roadmap-export-schema.md, src/utils/roadmapExport.js): a
// versioned, store-independent serialisation. Ids and timestamps are NOT
// included — import regenerates them via upsertNote's merge logic, so
// re-importing a file can never collide with existing note ids.

const SCHEMA_VERSION = 1

export function toNotebookSchema(notes) {
  return {
    version: SCHEMA_VERSION,
    notes: notes.map((n) => ({ date: n.date, subjectId: n.subjectId ?? null, text: n.text })),
  }
}

export function fromNotebookSchema(schema) {
  if (!schema || schema.version !== SCHEMA_VERSION) {
    throw new Error(`Unsupported notebook schema version: ${schema?.version}`)
  }
  return schema.notes.map((n) => ({
    date: n.date,
    subjectId: n.subjectId ?? null,
    text: n.text,
  }))
}
```

## Out of Scope (deliberate simplifications)

- **One note per (date, subjectId), not free-form multiple entries per day.** A student can't keep two separate general notes for the same day — editing always overwrites the single slot for that key. This matches the wireframe's single-textarea-per-day design and keeps merge-import unambiguous.
- **No AI-assisted note summarization or search** — plain text in, plain text out. Search/summarize is a plausible future epic, not this one.
- **No per-subject export** — Export/Import in `SchoolPanel` covers the whole notebook only; `SubjectDetailPanel`'s notebook section is browse-and-edit only, matching the PRD's singular "export my notebook" story rather than adding a second, narrower export surface.
- **No conflict resolution UI for import** — importing always overwrites the local note for a given `(date, subjectId)` with the file's version (last-write-wins), same as every other debounced-sync field in this codebase.
