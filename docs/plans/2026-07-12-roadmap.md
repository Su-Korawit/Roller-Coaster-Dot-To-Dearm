# Roadmap (delete blocks · remove color · fix report snap) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Idea:** `node-1-1783834449074` — Process "Roadmap" on the IR Board.

**Requirement (from the Idea's Process note, translated):**
1. Add a delete-block function.
2. Remove the change-color feature from the whole Roadmap page, for both Users
   and Admin.
3. The dot-to-dot block connection system is still buggy on Update — e.g. a
   newly appended Update block is not actually connected. Dig deep here.

**Interpretation (verified against the code):**
1. The user Roadmap (`RoadmapPage.jsx`) already deletes blocks three ways
   (drag-to-trash `TrashZone`, `deleteKeyCode`, `SelectionActionBar`). The IR
   Board (`IdeaRequestSection.jsx`) has **none** — no `deleteKeyCode`, no
   `onNodesDelete`, no trash zone. Requirement 1 therefore means: **add block
   deletion to the IR Board**, reusing the Roadmap's `TrashZone` + store
   actions.
2. The color feature is the swatch + hidden `<input type="color">` +
   `data.color` border in `ProcessNode`, `ConditionNode`, and `ImageNode`.
   These components are shared by the user Roadmap and the IR Board, so
   removing it there removes it from both pages at once.
3. `appendReportNode` (`src/lib/irBoard.js`) — the function `/ilovework` uses
   to put Update/Success blocks on the board — creates an (invisible) edge but
   positions the block at `root + (180, 40 + n·120)`, which is **not** a
   dot-to-dot snap position. Since edges render as `InvisibleEdge` (no line),
   the only visual signal of a connection is blocks touching dot-to-dot — so
   appended reports look disconnected, floating near the root. The fix: place
   each appended report **snapped** to the chain tail using the exact same
   `computeSnapPosition` math the canvas uses, and record the edge handles so
   the correct dots glow.

**Standing-rule note:** the "never modify user Roadmap behavior" rule is
overridden *only* for requirement 2, because this Idea explicitly asks to
remove the color feature from the Users page too. `StartNode` is not touched.
No other user-Roadmap behavior changes.

**Goal:** IR Board blocks can be deleted (trash-drag + Delete/Backspace); no
block has a color picker anywhere; blocks appended by `/ilovework` land
genuinely connected — snapped dot-to-dot with glowing dots.

**Architecture:** Reuse existing machinery — `TrashZone` + `removeNode` /
`removeEdge` store actions for IR deletion; delete the color-picker JSX from
the three node components and the `color` default from `addNode`; rework
`appendReportNode` to find the report-chain tail and snap the new block with
`computeSnapPosition(tail, report, 'bottom')`, forming a vertical timeline
under the Idea root (the root's right dot stays free for requirement blocks).

**Tech Stack:** React 18 (plain JSX, no TypeScript), @xyflow/react (React
Flow), Zustand (`useRoadmapStore`), Tailwind v4, Vitest + Testing Library
(jsdom), firebase-admin (scripts only).

### Task 3: Appended Update/Success blocks connect for real (dig deep)

**Root cause:** `appendReportNode` (`src/lib/irBoard.js:66-95`) writes the
report at `root + (180, 40 + n·120)` — an arbitrary offset, not a snap
position — and its edge omits handles. With `InvisibleEdge` there is no line,
so a block that isn't flush dot-to-dot *is* visually disconnected, and the
null-handle edge makes the wrong dots (left/right) glow even when the block
is repositioned. Every report also fans out from the root instead of
continuing the chain.

**Fix:** each appended report snaps to the **bottom** dot of the chain tail
(the root for the first report, the lowest existing report after that),
using `computeSnapPosition(tail, report, 'bottom')` — the exact math the
canvas snap uses — and the edge records
`sourceHandle: 'bottom', targetHandle: 'top'` so precisely those two dots
glow. The vertical timeline keeps the root's right dot free for requirement
(Process) blocks.

**Files:**
- Modify: `src/lib/irBoard.js` (`appendReportNode`)
- Test: `src/lib/irBoard.test.js`

**Interfaces:**
- Consumes: `computeSnapPosition`, `BLOCK_SIZES` from
  `src/utils/computeSnapPosition.js` (pure ESM — safe to import from both the
  browser bundle and `scripts/irReport.mjs` under Node).
- Produces: `appendReportNode({ nodes, edges, ideaId, type, summary })` —
  same signature; returned report node sits at the snap position and the
  returned edge carries `sourceHandle`/`targetHandle`. `scripts/irReport.mjs`
  needs no changes.

- [ ] **Step 3: Implement the chain snap**

In `src/lib/irBoard.js`:

```js
import { computeSnapPosition } from '../utils/computeSnapPosition.js'
```

Rewrite the placement part of `appendReportNode`:

1. Collect this idea's report nodes only (reuse `collectIdeaSubtree(ideaId,
   nodes, edges)` and filter `type === 'update' || type === 'success'`) so
   reports of *other* ideas never affect the tail.
2. `tail` = the report with the greatest `position.y`, or the root when the
   idea has no reports yet. (Max-y is deliberate: it also chains correctly
   under legacy fanned-out boards.)
3. Build the report node with
   `position: computeSnapPosition(tail, { type }, 'bottom')` — pass the new
   node's type so `BLOCK_SIZES` sizes both ends (`computeSnapPosition` only
   reads `type`/`measured` off the target).
4. Edge: `{ id: edgeId, source: tail.id, target: reportId, sourceHandle:
   'bottom', targetHandle: 'top' }`.
5. Delete the now-unused `existingReports` count.

`connectionMode="loose"` on both canvases already permits source-dot →
source-dot edges (bottom and top are both `type="source"` dots on
Update/Success/IdeaRoot), and `ConnectionDot` glows per-handle from either
end of an edge, so exactly the two joined dots light up.
