**Idea:** `node-10-1783857922378` — "ทำ Feature File Bag" on the IR Board.

**Requirement (from the Idea's Process blocks, translated):**
- `bag.ilovetcas.com` — open it to see what files currently exist: (1) all
  uploaded images/videos of any kind, (2) files exported from Roadmap/Calendar, (3) files
  from Roadmap.
- Everything a user has uploaded (files + text) shows on the Bag page. Limit: 1GB/user,
  1TB for Admin.
- Can pay to buy a 5GB/25GB plan, 29/59 THB per month.
- Files render as square blocks like the Roadmap page, just without connector dots.
- UX/UI: novel, like a macOS Desktop — drag items anywhere, create folders; a folder is
  itself another Desktop-like page.
- Ctrl+C / Ctrl+V / Ctrl+D (copy/paste/duplicate) support.
- A left-side feature icon rail whose visible icons are controlled by a Feature Setting;
  changing that setting must update what shows.
- Responsive — friendly to use, also works on phone and iPad.

**Scope decisions (the Idea leaves several things ambiguous; each is decided below with
its reasoning, so the implementer isn't guessing mid-build):**

1. **No guest mode, unlike other Feature sites.** ADR-0012 makes `roadmap`/`tcas`/`news`/
   `school` guest-usable (local-first, no Firebase Anonymous Auth). File Bag shows
   *previously uploaded* files — there is nothing to aggregate for a signed-out user, so
   `bag.ilovetcas.com` is `RequireAuth`-gated. This is a deliberate exception to ADR-0012's
   pattern, not an oversight — record it as ADR-0016 (Task 1) rather than silently
   deviating.
2. **"Exported from Roadmap/Calendar" and "from Roadmap" are the same underlying sources
   today.** Confirmed via code read: Roadmap's JSON export (`RoadmapPage.jsx:224-243`) and
   the School Notebook's export (`notebookExport.js` + `SchoolPanel.jsx:55-73`, the closest
   thing to "Calendar" in this codebase — there is no separate calendar/`.ics` export
   anywhere) are both pure client-side download-to-browser flows with **no** Storage/
   Firestore persistence today. There's also no existing "my past exports" list. Rather
   than build two unrelated aggregation mechanisms, this plan adds one new "Save to Bag"
   option next to each existing download button (Task 8) — clicking it uploads the same
   blob to Storage and creates a File Bag item, satisfying "files exported from
   Roadmap/Calendar" literally without inventing a second export format.
3. **Existing per-user Roadmap uploads (images/videos/files attached to roadmap nodes)
   get retrofitted to also register in File Bag**, rather than listed live from Storage at
   read time. Today `uploadRoadmapImage.js`, `VideoPickerModal.jsx`, and
   `FilePickerModal.jsx` write straight to Storage (`users/{uid}/roadmap{,-video,-file}/…`)
   with no Firestore doc — so there's nothing to rename/move/organize from the Bag side.
   Task 5 adds one additional Firestore write after each existing successful upload,
   non-breaking, so every roadmap-attached file also becomes a normal Bag item the user can
   drag into a folder like anything else. (The alternative — listing Storage directly at
   read time — would produce second-class items that can't be organized; rejected.)
4. **Data model: two new top-level Firestore collections**, `fileBagItems` and
   `fileBagFolders`, each with an `ownerUid` field — following the `roadmapSheets`
   precedent (`src/lib/db.js`) for "many docs owned by one user, unbounded count," not a
   `users/{uid}/files` subcollection, so the same `refs`/`cols`/`queries` factory shape
   this codebase already uses for owned-collections applies directly.
5. **Storage path for Bag-native uploads (files dragged straight into the Bag, not via
   Roadmap):** `users/{uid}/bag/{itemId}-{filename}`. Roadmap-sourced items (see decision
   #3 above) keep their existing Storage path — File Bag only adds a Firestore pointer to
   them, it never copies/moves the underlying object.
6. **Canvas: reuse `@xyflow/react` (React Flow), not `@hello-pangea/dnd`.** Confirmed via
   code read: `@hello-pangea/dnd` (already in `package.json`) is a linear/axis-constrained
   list-reorder library with no free (x,y) placement and no droppable-inside-draggable
   nesting — the wrong tool for "drag anywhere, make folders." React Flow already gives
   free positioning, multi-select marquee (**Selection** vocab), a **Trash zone** drop
   pattern, and `useLongPressDrag` for touch — all directly reusable, and it's already a
   dependency. Bag nodes carry no edges; node types are `BagFileNode`/`BagFolderNode`.
   "A folder is its own Desktop page" is implemented as a `currentFolderId` filter over the
   same canvas (open folder → node set swaps to that folder's children), not real
   navigation/routing.
7. **Responsive scope-cut for the free-canvas metaphor:** a macOS-Desktop-style free-form
   canvas is a poor fit under ~768px. Below the `md` breakpoint, Bag renders a **grid/list
   view** instead (reusing `AssetsManagerSection.jsx`'s existing responsive folder-grid
   pattern, `AssetsManagerSection.jsx:287`, already proven at 375px) with the same
   create-folder/move/rename actions available as buttons/long-press-menu instead of free
   drag. The free-form canvas activates at `md:` and above. This still satisfies "responsive
   … works on phone and iPad" (the Idea's own explicit ask) without forcing a
   drag-precision interaction onto a touchscreen the size of a phone.
8. **Ctrl+D duplicate = reference, not a physical file copy.** Duplicating a file inside
   the Bag creates a new `fileBagItems` doc pointing at the *same* `storagePath`, not a new
   Storage object — avoids doubling both the user's Storage footprint and their quota usage
   for what's conceptually "put this here too." Flagged explicitly since "duplicate" could
   also mean a real copy; this plan picks the cheaper, quota-safe interpretation.
9. **Quota (1GB/5GB/25GB/1TB) is enforced by a Cloud Function reservation, not client-only
   or Storage Rules.** Storage Rules can't do cross-object aggregate size checks. Mirrors
   the app's existing "Coins/entitlements are Functions-owned" pattern
   (`firestore.rules` excludes them from client writes): a new `reserveBagUpload(sizeBytes)`
   callable atomically checks `users/{uid}.fileBagUsageBytes + sizeBytes <= quota` and
   reserves it before the client is allowed to start the Storage upload (same
   reserve-then-confirm shape as `createPurchase`'s `WAITING_PAYMENT` step). A Storage
   `onDelete` trigger releases the reservation when a Bag item's underlying object is
   deleted (only for Bag-native paths — Roadmap-sourced references don't own the byte
   count, since deleting them from the Bag doesn't delete the underlying roadmap file).
10. **Paid plans reuse the existing Entitlement + Coins + PromptPay chain end to end, with
   zero Cloud Function changes to the payment path itself.** Confirmed via code read:
   entitlements are bought with Coins (`purchaseEntitlement`), Coins are bought with
   PromptPay+SlipOK (`createPurchase`/`verifyPayment`) — there's no direct
   PromptPay→entitlement shortcut today, and building one would mean new Function branches.
   This plan adds two `entitlementCatalog` docs (`kind: 'storage-quota'`,
   `payload: { extraBytes }`, priced in Coins) and a `useEntitlementsStore` reducer
   `extraStorageBytes()` — the existing "buy Coins, spend Coins on an entitlement" flow
   (already shipped, e.g. `UnlockSection.jsx`) is reused verbatim. The 29/59 THB monthly
   prices from the Idea note become their Coins-equivalent price on the catalog doc (Coins
   pricing conversion is an admin/business decision, not a code decision — flag for the
   idea owner to set the actual Coins price when seeding the catalog doc, default to a
   placeholder in the seed script).
11. **"Feature Setting" left rail visibility control** is a small new per-user doc
   (`bagSettings/{uid}`, `{ visibleCategories: string[] }`) read by the Bag page to decide
   which left-rail icons render (Images / Videos / Files / Exports / Trash) — a settings
   panel toggles entries in that array. Not tied to the global Admin "Feature Setting"
   concept (that's a different, admin-facing thing per `IdeaRequestSection.jsx`'s note
   text) — this is a per-user preference, scoped to `bagSettings`.

**Goal:** A signed-in user visiting `bag.ilovetcas.com` sees every file they've ever
uploaded (roadmap image/video/file nodes, plus anything saved from Roadmap/Notebook export,
plus anything dragged straight into the Bag) as square blocks on a free-form
Desktop-style canvas (md+) or a responsive grid (mobile), organized into folders, with
Ctrl+C/V/D support, a 1GB free quota enforced server-side, and an upgrade path to 5GB/25GB
via the existing Coins/PromptPay purchase flow.

**Architecture:** See scope decisions above for the "why." Summary of the "what":
- **New site key `bag`** added to `src/lib/site.js`'s site-key resolution (ADR-0012
  pattern), new route tree entry in `App.jsx`, wrapped in `FeatureLayout` **plus**
  `RequireAuth` (the ADR-0012 exception from decision #1).
- **Firestore additions** (`src/lib/db.js`): `refs.fileBagItem(id)` / `cols.fileBagItems`
  / `queries.fileBagItemsByOwner(uid)` / `queries.fileBagItemsByFolder(uid, folderId)`;
  same shape for `fileBagFolders`; `refs.bagSettings(uid)` (private-doc pattern, like
  `refs.spotifyAuth`). `shapes.fileBagItem(...)` factory for the write shape:
  `{ ownerUid, storagePath, name, kind: 'image'|'video'|'file'|'export', source:
  'bag-upload'|'roadmap-image'|'roadmap-video'|'roadmap-file'|'roadmap-export'|
  'notebook-export', folderId: string|null, sizeBytes, createdAt }`.
- **`fileBagUsageBytes`** lives on `users/{uid}`, Functions-owned (excluded from client
  writes in `firestore.rules`, same pattern as `coins`/`entitlements`).
- **Cloud Functions** (`functions/index.js`): `reserveBagUpload(sizeBytes)` callable
  (reserve-then-upload, mirrors `createPurchase`'s reservation shape); a Storage `onDelete`
  trigger on `users/{uid}/bag/**` that decrements `fileBagUsageBytes` and cleans up any
  orphaned `fileBagItems` doc.
- **Storage rules**: new `match /users/{uid}/bag/{fileId}` block, owner-only read *and*
  write (stricter than the existing `roadmap{,-video,-file}/` rule, which allows any
  signed-in user to read — deliberately not copied verbatim, per the private-by-default
  intent of a personal file manager).
- **Canvas**: `src/pages/BagPage.jsx` (new), `src/components/bag/BagCanvas.jsx` (React
  Flow, no edges), `BagFileNode.jsx`/`BagFolderNode.jsx` (square blocks, no connector
  handles), reusing `TrashZone`, `useLongPressDrag`, and the Selection concept from
  `components/roadmap/*` (import directly — these are generic enough not to be
  Roadmap-specific; if any turn out to hardcode Roadmap assumptions, extract the shared
  part rather than forking it).
- **Mobile/tablet fallback**: `src/components/bag/BagGridView.jsx` (new, < `md`), modeled
  on `AssetsManagerSection.jsx`'s existing responsive grid.
- **Upload flow**: drag file onto canvas (or tap "+" on mobile grid) →
  `reserveBagUpload(file.size)` → on success, `uploadAsset('users/{uid}/bag/...', file)`
  (reuse `storageOps.js`, same as every other upload path in the app) → create
  `fileBagItems` doc. On reservation failure (over quota), show the upgrade-plan CTA.
- **Retrofit** (decision #3): `uploadRoadmapImage.js`, `VideoPickerModal.jsx:43`,
  `FilePickerModal.jsx:49` each gain one additional `fileBagItems` doc write after their
  existing `uploadAsset` call succeeds — additive, no change to their existing return
  values or callers.
- **Export-to-Bag** (decision #2): a new button next to the existing download button in
  `RoadmapPage.jsx`'s export UI and `SchoolPanel.jsx`'s notebook export UI — same
  reserve → upload → create-doc flow as any other upload, `source: 'roadmap-export'` /
  `'notebook-export'`.
- **Ctrl+C/V/D**: keyboard handlers scoped to `BagCanvas` (only active while it has focus/
  is mounted) — copy stores selected item ids in a local ref/state, paste/duplicate create
  new `fileBagItems` docs referencing the same `storagePath` (decision #6), never touch
  Storage.
- **Entitlements**: two new `entitlementCatalog` seed docs (`storage-quota` kind,
  5GB/25GB `payload.extraBytes`), `useEntitlementsStore.js` gains `extraStorageBytes()`
  reducer (`owned(entitlements, 'storage-quota').reduce((sum, e) => sum + e.payload.
  extraBytes, 0)`, mirroring the existing `plan-slots`/`ai-quota` reducers). Total quota
  displayed/enforced = `1GB + extraStorageBytes()`, or flat 1TB for admin emails
  (`ADMIN_EMAILS`).
- Standing rules: no deploys of rules/Functions from this plan directly — per `/iloveplan`
  standing rules, queue `firestore.rules`/`storage.rules`/Functions deploys into
  `.iloveskill/pending-deploys.json` instead of deploying manually. No `StartNode` / user
  Roadmap *behavior* changes (the retrofit in Task 5 is additive-only, verify with existing
  Roadmap tests before/after).

**Tech Stack:** React 19 JSX (no TS), Tailwind v4, `@xyflow/react` (already a dependency —
no new drag library), Firebase Firestore/Storage/Functions, Vitest + Testing Library. No
new npm dependencies.
